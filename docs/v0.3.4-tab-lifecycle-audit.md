# تدقيق دورة حياة التبويبات والموارد في X-Pilot v0.3.4

## الخلاصة التنفيذية

لا توجد مؤشرات على تسريب مستمعات `onUpdated` أو مؤقتات `setTimeout` في مسار الانتظار الطبيعي؛ فالمستمع والمؤقت يُنظفان عند اكتمال التحميل أو انتهاء المهلة. كما أن الإضافة تستخدم اسم Alarm واحدًا، لذلك لا تنشئ عددًا متزايدًا من Alarms المتوازية.

مع ذلك، لا يمكن تأكيد خلو الإصدار `v0.3.4` من تسريبات الموارد. التدقيق كشف مشكلتين فعليتين في دورة حياة الموارد، إضافة إلى ملاحظة تصميمية تتعلق بالتبويب الدائم. أهم مشكلة هي أن `inspectTab` قد يعيد حقن `content.js` في كل محاولة فاشلة، مما قد يسجل مستمع `chrome.runtime.onMessage` مكررًا داخل الصفحة. والمشكلة الثانية هي أن تبويب بنك الروابط لا يُغلق إذا وقع استثناء بعد إنشائه وقبل تنفيذ `chrome.tabs.remove`.

## النتائج

| المعرف | النتيجة | الخطورة | الحالة في v0.3.4 |
|---|---|---:|---|
| TAB-01 | إعادة حقن Content Script عند كل فشل في إرسال الرسالة | عالية | موجود |
| TAB-02 | عدم إغلاق تبويب البنك عند الاستثناء | متوسطة | موجود |
| TAB-03 | تبويب الأتمتة يبقى مفتوحًا حسب الإعداد الافتراضي | منخفضة، تصميمية | مقصود جزئيًا |
| TAB-04 | مستمع `onUpdated` والمؤقت داخل `waitForTabLoad` | منخفضة | لا يوجد تسريب واضح |
| TAB-05 | Alarm والـ timers العامة | منخفضة | لا يوجد تراكم واضح |

## TAB-01: خطر إعادة حقن Content Script

في `service-worker.ts`، ترسل الدالة `inspectTab` رسالة `X_INSPECT`. إذا فشلت الرسالة، تنفذ `chrome.scripting.executeScript` لحقن `content.js` ثم تعيد إرسال الرسالة. وتُستدعى هذه الدالة كل 500 مللي ثانية تقريبًا من `waitForPublishReady`.

في `content-entry.ts`، يضيف كل تنفيذ لـ `content.js` مستمعًا جديدًا إلى `chrome.runtime.onMessage`. لذلك، إذا فشل إرسال الرسالة بسبب تأخر التهيئة أو حالة انتقالية في X، يمكن أن يحدث التسلسل التالي:

```text
فشل X_INSPECT
حقن content.js رقم 1
فشل مؤقت في الرسالة التالية
حقن content.js رقم 2
فشل مؤقت في الرسالة التالية
حقن content.js رقم 3
```

النتيجة ليست بالضرورة تسريب JavaScript دائمًا، لكنها تؤدي إلى مستمعين مكررين داخل نفس الصفحة. ومع كل رسالة لاحقة قد تُنفذ `inspect()` أو `publish()` أكثر من مرة. هذا خطر وظيفي وذاكري حقيقي، ويجب اعتباره أولوية عالية.

### الإصلاح المقترح

يجب استخدام قفل لكل تبويب يمنع تكرار الحقن المتزامن، مع محاولة واحدة فقط للحقن خلال دورة الصفحة. ويمكن أيضًا إضافة حارس داخل `content-entry.ts` باستخدام `globalThis` حتى لا يسجل المستمع أكثر من مرة:

```ts
const key = '__xPilotContentListenerInstalled';
if (!(globalThis as Record<string, unknown>)[key]) {
  (globalThis as Record<string, unknown>)[key] = true;
  chrome.runtime.onMessage.addListener(/* listener */);
}
```

والأفضل أن تكون عملية الحقن عبر `ensureContentScript(tabId)` تحفظ حالة الحقن لكل تبويب، وتحذف الحالة عند إزالة التبويب أو عند بدء تنقل جديد.

## TAB-02: تبويب بنك الروابط لا يُغلق عند الاستثناء

تنشئ `extractBank` تبويبًا للخلفية ثم تنتظر التحميل وتنفذ `executeScript`. يتم استدعاء `chrome.tabs.remove(tab.id)` بعد تنفيذ السكربت فقط. إذا فشل الانتظار أو حقن السكربت أو قراءة النتيجة، يخرج التنفيذ من الدالة قبل الوصول إلى `tabs.remove`، ويبقى تبويب البنك مفتوحًا.

### الإصلاح المقترح

يجب وضع إزالة التبويب في `finally`، مع تجاهل خطأ الإزالة إذا كان المستخدم أو المتصفح قد أغلق التبويب مسبقًا:

```ts
let bankTabId: number | undefined;
try {
  const tab = await chrome.tabs.create({ url: bankUrl, active: false });
  bankTabId = tab.id;
  // wait, extract, parse
} finally {
  if (bankTabId) await chrome.tabs.remove(bankTabId).catch(() => undefined);
}
```

## TAB-03: تبويب الأتمتة الدائم

تحتوي الإعدادات على `keepAutomationTabOpen` و`closeTabOnComplete`، لكن مسار `STOP` ومسار إكمال الجلسة لا يغلقان التبويب ولا يطبقان هذين الإعدادين في الكود الحالي. التبويب لا يتكاثر لأن الإضافة تعيد استخدام `automationTabId` نفسه، لذلك لا يظهر تسريب غير محدود عند تشغيل Queue مرات متتالية. لكنه يظل موردًا مفتوحًا بعد اكتمال الجلسة، حتى عندما يطلب إعداد المستخدم إغلاقه.

### الإصلاح المقترح

يجب إضافة دالة موحدة مثل `closeAutomationTabIfConfigured(session)` واستدعاؤها في الحالات التالية:

- اكتمال Queue.
- `STOP`.
- فشل نهائي مع `PAUSE` إذا كان الإعداد يطلب الإغلاق.
- إزالة الإضافة أو تلف التبويب.

بعد الإغلاق يجب حذف `automationTabId` من الحالة ومن المفتاح المنفصل `automationTabId` في التخزين.

## TAB-04: مستمع التحميل والمؤقت

يضيف `waitForTabLoad` مستمعًا واحدًا إلى `chrome.tabs.onUpdated` ومؤقتًا واحدًا لكل استدعاء. عند اكتمال التحميل، تستدعي الدالة `finish` التي تزيل المستمع وتلغي المؤقت. وعند انتهاء المهلة، تنفذ عملية التنظيف أيضًا.

وجود استدعاء `chrome.tabs.get` بالتوازي مع مستمع `onUpdated` لا يسبب تسريبًا؛ فالحالة `settled` تمنع التسوية المتكررة، و`cleanup` يزيل المستمع ويلغي المؤقت. لا توجد حاجة إلى تغيير هذا الجزء سوى تحسين أسلوب التعامل مع خطأ `tabs.get` أو إضافة اختبار محاكاة.

## TAB-05: Alarms والمؤقتات

يستخدم الكود اسم Alarm ثابتًا هو `x-queue-next-item`. استدعاء `chrome.alarms.create` بالاسم نفسه يستبدل Alarm السابق بدل إنشاء مجموعة غير محدودة. كما أن دالة `wait` تنشئ مؤقتًا قصير العمر ينتهي تلقائيًا ولا تحتفظ به في مصفوفة أو مرجع دائم.

مع ذلك، يفضل استدعاء `chrome.alarms.clear(ALARM_NAME)` قبل إنشاء Alarm في مسارات الاستئناف أيضًا، وذلك لتوحيد السلوك وتقليل احتمال وجود Alarm قديم عند تغير الحالة بسرعة.

## الحكم النهائي

الحكم ليس «خلو كامل من التسريب». الإصدار `v0.3.4` آمن في إدارة مستمع التحميل والمؤقتات الأساسية، لكنه يحتاج إلى إصلاحين قبل اعتبار دورة حياة التبويبات سليمة:

1. منع إعادة حقن `content.js` وتسجيل مستمعين مكررين.
2. ضمان إغلاق تبويب البنك باستخدام `finally`.

كما ينبغي تطبيق إعدادات إغلاق تبويب الأتمتة بدل إبقائه مفتوحًا بعد اكتمال الجلسة. أوصي بإنشاء إصدار إصلاح مخصص، مثل `v0.3.5`، يبدأ بـ `TAB-01` و`TAB-02` ثم يضيف اختبارات دورة حياة للتأكد من عدم تكرار الحقن وعدم بقاء التبويبات بعد الاستثناءات.
